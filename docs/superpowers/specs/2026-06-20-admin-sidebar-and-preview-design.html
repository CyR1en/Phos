Admin Layout — Design Spec

Resizable sidebar, icon-only collapse rail, and right-side site preview

Date: 2026-06-20 Status: Draft — pending user review Scope: Admin SPA layout, three new affordances Stack: Preact (compat), TanStack Query, Tailwind v4, localStorage

1. Context & Problem

The admin SPA today has a fixed-width (256 px) sidebar that takes up a constant fraction of the viewport, and a main content area with substantial unused horizontal space on the right (especially on wide screens). The user wants three things:

  1. Resizable sidebar — drag the right edge to make the sidebar smaller than its default, down to a minimum that still fits the widest nav item.
  2. Collapsible sidebar — toggle the sidebar to a thin icon-only rail.
  3. Live site preview — use the empty space on the right to render an iframe of the public site, with auto-refresh on save and auto-navigation when the user switches admin pages.

All three persist across reloads via localStorage. Mobile (< 768 px) keeps the existing Preline overlay sidebar; the preview is desktop-only.

2. Goals & Non-Goals

Goals

  • Make the admin layout fit more comfortably on wide screens without forcing a 256 px sidebar.
  • Preserve every existing nav affordance; collapse should not lose the ability to navigate.
  • Give the user visual feedback on config changes without leaving the admin.
  • Persist UI preferences across reloads.

Non-Goals

  • Rewriting or replacing the existing Preact/TanStack Query stack.
  • Live edit-and-preview (preview is post-save, not real-time as you type).
  • Cross-device sync of UI preferences.
  • Mobile (under md) support for resize, collapse, or preview — these are desktop features.
  • Visual redesign of the sidebar, header, or nav items themselves — only the layout around them changes.

3. New Admin Layout

New / interactive Sidebar / preview surfaces Main content

The wrapper element exposes two CSS custom properties — --sidebar-width and --preview-width — that drive every layout dimension. This keeps the three panels in sync without prop-drilling widths through the tree.

4. Feature 1 — Resizable Sidebar (shrink only)

Behavior

  • A 4 px-wide vertical handle sits on the sidebar's right edge.
  • Cursor: ew-resize. Visible on hover (handle darkens from border-border to border-primary; hit area is 8 px even when the visual is 4 px).
  • Drag left shrinks the sidebar. Drag right is clamped at w-64 (256 px) — the user cannot grow the sidebar past its current default.
  • While dragging: document.body cursor is forced to ew-resize and user-select: none is set so text selection doesn't fight the drag.
  • On mouseup: width is committed to localStorage under admin.sidebar.width.

Minimum width — dynamic measurement

On mount (and on theme change, since font widths can differ), measure the scrollWidth of every nav button, section header, and footer row, take the max, add 24 px for horizontal padding, and use that as the resize floor.

Why dynamic: the spec calls for "as small as the widest tab/entry". Hard-coding a floor would either truncate long labels or waste space on shorter ones. The current widest labels are Categories, Galleries, and the section header Extensions — dynamic measurement is the only way to honor new labels added in the future.

Fallback: if measurement fails or returns 0, default to 160 px. Cap the result at 240 px so the floor is never unreasonably close to the default.

Implementation outline

function Sidebar() {
  const [width, setWidth] = useLocalStorageState('admin.sidebar.width', 256)
  const [minWidth, setMinWidth] = useState(160)
  const sidebarRef = useRef<HTMLElement>(null)

  useEffect(() => {
    if (!sidebarRef.current) return
    const nodes = sidebarRef.current.querySelectorAll(
      '[data-measure="nav-item"], [data-measure="nav-header"]'
    )
    let max = 0
    nodes.forEach((n) => { max = Math.max(max, (n as HTMLElement).scrollWidth) })
    setMinWidth(Math.max(120, Math.min(240, max + 24)))
  }, [/* re-run on theme toggle */])

  // ...dragging handled by a tiny custom hook or inline mousedown/move/up
}

5. Feature 2 — Collapsible Sidebar (icon-only rail)

Behavior

  • Add a chevron toggle button to the sidebar header (right side). Replaces the current mobile-only close button on desktop; the mobile close button is still rendered on mobile via md:hidden.
  • Two states: full (default) and icon-only.
  • State persists in localStorage under admin.sidebar.collapsed.
  • When icon-only:
    • Width → 56 px (size-14 rail).
    • All nav item labels and section headers hidden.
    • Icons centered.
    • Existing Tooltip component wraps each icon button to show the full label on hover.
    • Footer collapses to a single status dot (no "System Active" text, no version).
    • Resize handle hidden (a 56 px rail is not resizable).
    • Sidebar header: logo + "Phos Admin" title also hide; the toggle button remains, paired with a small icon-only logo mark if desired.
  • Mobile (< md): collapse toggle does nothing — mobile uses the existing overlay pattern.

State matrix

icon-only 56 px Hidden Hidden Yes

6. Feature 3 — Site Preview Panel (right side)

Layout

  • A new column to the right of <main>. Default width 480 px.
  • Resizable from its left edge (mirror of the sidebar's handle), 320–800 px clamp. Width persists in localStorage under admin.preview.width.
  • Visible/hidden toggle. A small "Preview" button in the top header bar (next to the existing Save / Republish / Sign-out group) flips a boolean persisted at admin.preview.visible.
  • On mobile (< md): the preview button is hidden, the panel is not rendered.

Panel header

A small 32 px-tall bar at the top of the panel:

  • URL display — shows the current iframe path. Clicking turns it into an input for manual URL entry; pressing Enter or blurring navigates the iframe. This is the only "navigation" affordance; no back/forward, no address-bar chrome.
  • Refresh button — re-loads the iframe.
  • Close button — hides the panel and sets admin.preview.visible = false.

Iframe

  • Single <iframe> element filling the rest of the panel.
  • Same-origin (the admin and the public site are served from the same host), so no CORS, no sandbox attribute needed.
  • Initial src: / on first load (or whatever admin.preview.lastUrl says, if present).

Refresh strategy

The iframe reloads on two triggers:

  1. Manual — clicking the refresh button in the panel header.
  2. Auto on save — when saveStatus transitions to 'saved' in the store, the panel re-loads the iframe. (We do not refresh on every keystroke or on 'dirty' — the debounce is 1.5 s, and the user is still typing.)
Caveat: the public site reflects the last built config, not the just-saved config. So in practice, the iframe reloads on 'saved' but shows the previous build until 'done' arrives from the build task poller. Recommended follow-up (out of scope for this spec): also re-load on 'done' so the preview picks up the rebuilt site without a manual refresh. Follow-up

Page-to-public-route mapping

When the user navigates between admin pages, the iframe URL auto-navigates to the closest public equivalent (if one exists):

Admin pagePreview URLNotes
site / Site config is global; home is a reasonable representative
home / Direct mapping
about /about/ Direct mapping
contact /contact/ Direct mapping
notFound (no mapping) Iframe URL unchanged. The static 404 page isn't directly servable (internal in nginx).
categories (no mapping) Admin-only; iframe URL unchanged
galleries /galleries/ Direct mapping
plugins (no mapping) Admin-only; iframe URL unchanged

For unmapped pages, the iframe URL stays on the last public route the user (or auto-navigate) set. This avoids the surprise of the preview jumping to / every time the user opens the Categories tab.

The mapping lives in a small constant in PreviewPanel.tsx:

const PAGE_TO_PUBLIC_ROUTE: Record<string, string> = {
  site:      '/',
  home:      '/',
  about:     '/about/',
  contact:   '/contact/',
  galleries: '/galleries/',
  // notFound, categories, plugins: no entry → iframe URL unchanged
}

7. State & Persistence

All UI state is local to the admin SPA and persisted in localStorage. No server-side involvement. All keys are namespaced under admin. to avoid collisions with the public site's own localStorage usage.

KeyTypeDefaultRange / clamp
admin.sidebar.widthnumber (px)256min = dynamic, max = 256
admin.sidebar.collapsedbooleanfalse—
admin.preview.visiblebooleantrue—
admin.preview.widthnumber (px)480320–800
admin.preview.lastUrlstring/Path only (no origin)

Storage helper

A tiny useLocalStorageState hook (new file src/lib/admin/useLocalStorageState.ts) wraps useState with a useEffect sync. It:

  • Reads the initial value from localStorage (or uses the supplied default on parse error / privacy mode).
  • Writes back on every change, wrapped in try/catch for environments where localStorage throws.
  • Listens to the 'storage' event so two open admin tabs stay in sync.

9. UX Details & Edge Cases

Resize handle hit area

Visual width is 4 px but the click target is 8 px (use a transparent hit-area div over a 4 px visible line). This is the same pattern VS Code uses for its sidebar drag handle.

Resize while typing in a field

Mouse events on the resize handle do not steal focus from any active input/textarea in the main content. Confirmed by handle's e.preventDefault() on mousedown.

Save status race

If the user saves twice in quick succession (rare but possible with Cmd+S), the iframe reloads once per 'saved' transition. That's fine — reloads are idempotent.

Initial preview URL

On first ever visit, admin.preview.lastUrl is unset. Default to / and persist it as soon as the panel mounts.

Theme switch

The dynamic sidebar min-width re-measures on theme change because Cormorant Garamond (the display font used in some labels) can have different widths in light vs. dark rendering at the same size.

Resize clamp on the preview

Min 320 px (smaller and the iframe is unusable). Max 800 px (larger and the main content area collapses to a useless strip on most screens).

10. Assumptions

  • A1. The user is on a desktop browser when using these features. Mobile is out of scope per the user's request. Assumed
  • A2. The public site is reachable from the admin's origin in the same browsing context (no separate domain). This holds for the project's current deployment. Assumed
  • A3. The existing mobile sidebar (Preline overlay) keeps working without change. The collapse and resize features are desktop-only. Assumed
  • A4. "Auto-navigate to match the public route" means: when an admin page has a public equivalent, switch the iframe. When it doesn't, leave the iframe alone. Assumed
  • A5. "Auto-reload when config saves" means: reload the iframe when saveStatus becomes 'saved'. We do not also reload on 'done' (the build task completing) — see §6 callout for the recommended follow-up. Assumed
  • A6. The chevron collapse toggle replaces the current mobile-only close button on desktop only. On mobile it continues to behave exactly as today. Assumed
  • A7. The sidebar logo + "Phos Admin" title also collapse in icon-only mode. A small icon-only mark (or just the toggle button) stays in the header. Assumed
  • A8. Resize handle hit area is 8 px even when the visual line is 4 px (industry-standard pattern, avoids frustrating the user). Assumed
  • A9. No new dependencies. All three features are implementable with Preact, the existing Tooltip component, and inline event handlers. Assumed

11. Verification Plan

Build

  1. npm run build exits 0 with no new warnings.

Sidebar resize (desktop)

  1. Drag the sidebar's right edge left — width decreases, main content's left margin shrinks accordingly.
  2. Try to drag past the widest nav item — clamp engages, no labels are truncated.
  3. Try to drag right past 256 px — clamp engages at 256 px.
  4. Reload the page — width persists at the last value.

Sidebar collapse (desktop)

  1. Click the chevron — sidebar shrinks to 56 px, labels and section headers hide, icons show tooltips on hover.
  2. Footer collapses to a single status dot.
  3. Resize handle is gone in collapsed state.
  4. Click the chevron again — sidebar expands back to its previous width with labels restored.
  5. Reload — collapsed state persists.
  6. Resize the window to mobile (< 768 px) — collapse toggle has no effect, mobile overlay still works.

Preview panel (desktop)

  1. Click the "Preview" toggle in the top header — panel appears on the right at 480 px wide, showing the home page in an iframe.
  2. Drag the preview's left edge — width changes between 320 and 800 px.
  3. Click the URL display — it becomes editable; type a path like /galleries/ and press Enter — iframe navigates.
  4. Click the refresh button — iframe reloads.
  5. Edit a config field, wait for the save indicator to show "saved" — iframe auto-reloads.
  6. Switch from the Home admin page to About — iframe navigates to /about/. Switch to Categories — iframe URL stays where it was (Categories has no mapping).
  7. Click the close button on the preview header — panel hides, main content's right margin collapses to 0.
  8. Reload — visibility + width + last URL all persist.

Regression

  1. All existing admin pages still render and save correctly.
  2. The mobile overlay sidebar still opens and closes via the hamburger button.
  3. Config save, republish, and regenerate flows still work end-to-end.

12. Out of Scope (Explicitly)

  • Live edit-and-preview (sub-second feedback while typing).
  • Auto-reload on buildStatus === 'done' (a recommended follow-up noted in §6).
  • Mobile (< md) support for resize, collapse, or preview.
  • Cross-device sync of UI preferences.
  • New dependencies (e.g., react-resizable-panels) — keeping the bundle lean.
  • A separate full-page preview route (e.g., /admin/preview/) — the iframe inline in the dashboard is enough.

13. Risks & Open Questions

  • Performance of dynamic width measurement: querySelectorAll on every theme toggle is O(n) on the number of nav items. With ~7–10 items, this is microseconds — not a real concern. Defer
  • Preview refresh on 'done': noted in §6 callout. If the build is slow (>5 s) the user will see stale content in the preview between save and build completion. Out of scope for MVP; can be added later. Verify post-MVP
  • Iframe sandboxing: not needed because the iframe is same-origin. If the public site ever moves to a different origin, the iframe will need sandbox attributes and possibly postMessage for refresh. Defer
  • Storage quota: 5 small keys, no concern.
